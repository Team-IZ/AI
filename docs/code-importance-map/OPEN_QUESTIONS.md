# code-importance-map 열린 질문

구현을 막지는 않지만, 결론 없이 넘어가면 안 되는 항목들. 코드 여러 곳(주로

## D8 — LLM 호출 vs 도구 호출, 회계 단위를 어떻게 나눌지

**상태: 미결. 아무것도 이 결론에 암묵적으로 의존하지 않는다.**

문제: `budgets/llm_budgets.json`의 `max_llm_calls`(실제 모델 완성 호출)와
`max_tool_rounds`(에이전트가 mid-reasoning에 하는 도구 호출)을 일부러 분리된
필드로 뒀다. 도구 호출 1건과 실제 모델 완성 호출 1건은 과금·지연 단위가
다른데, 이걸 하나의 "API 호출" 숫자로 뭉개면 비용/지연 분석이 어긋난다.

지금 상태: Phase 4에서는 크루에 도구를 아예 주지 않아서(`crew.py`의 D12 결정 —
`tools=[]`) `max_tool_rounds`가 실질적으로 쓰이지 않는다. 그래서 이 질문은
당장 급하지 않지만, 나중에 도구를 쓰는 스테이지가 추가되면 바로 결론이 필요하다.

검토할 두 방향(어느 쪽도 아직 채택 안 함):

1. **discriminator 필드.** `AiUsageEntry`에 `call_kind: Literal["COMPLETION", "TOOL"]`을
   추가해 도구 호출도 한 행씩 남긴다. 장점: 원장이 하나. 단점: `ai_usage`는 Spring
   DB 테이블이라 컬럼 추가는 Backend 협의가 필요하고(이미 C-3/C-4로 대기 중),
   도구 호출 행은 토큰 수가 0이라 비용 합계를 오염시킬 수 있다.
2. **원장을 둘로.** `AiUsageEntry`는 지금처럼 완성 호출 전용으로 두고, 도구
   호출은 별도 내부 지표(예: 완성 호출 행에 `tool_call_count`/`tool_latency_ms`를
   덧붙이거나 완전히 out-of-band로 기록)로 뺀다. 장점: Backend 계약 변경 없이
   바로 적용 가능. 단점: "시간이 어디서 샜는지"를 보려면 출처가 두 곳으로 나뉜다.

**결정 필요 시점:** 도구를 실제로 쓰는 다음 스테이지를 만들기 전.

## D10 — README의 "코드 분석 응답 = 6콜" 계약이 실제와 다름

**상태: 백엔드/팀 논의 필요, 여기서 결론내리지 않음.**

`README.md:308`는 "LLM 호출 1건 = 배열 원소 1개이므로, 코드 분석 응답에는
6개가 들어간다"고 명시하고, `PLAN_FASTAPI_MIGRATION.md` §규모는 이 "팀당
6콜"을 근거로 "30팀 = 180콜 ≈ 4.5분(40rpm 기준), Redis 불필요·워커 1개 유지"
용량 계산을 한다.

codemap 스테이지가 실제로 몇 콜을 쓰는지는 크루의 tool-loop 여부에 달려 있어
6으로 고정되지 않는다(Phase 4에서는 도구가 없어 매 제출물당 최대 1콜이지만,
나중에 도구 스테이지가 붙으면 늘어난다). 이 브랜치의 어떤 코드도 "6"이라는
숫자에 의존하지 않는다 — 호출 상한은 전부 `budgets/llm_budgets.json`에서만
온다. `README.md`도 이 브랜치에서 손대지 않았다.

**논의할 한 줄:** README의 회당 호출 수가 "계약"인지 "문서상 추정치"인지 —
전자라면 codemap 스테이지가 그 안에 맞춰야 하고, 후자라면 숫자를 재협상해야 한다.

**결정 필요 시점:** codemap을 실제 파일럿(운영 세션)에 붙이기 전 --
`PARALLEL_RUN_CHECKLIST.md`의 PR-3 실측 절차가 진행되면 실제 호출 수가
자연히 나오므로, 그 데이터를 들고 이 논의를 다시 열 것.
